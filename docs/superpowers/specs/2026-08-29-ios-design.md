# A third shell: iOS

Status: **design.** Nothing built.

## The idea

The same move as Android, and for the same reason. The geometry core is C++
behind a narrow loopback HTTP API, and the interface is a React page that does
not care what is on the other end of it. Android was 692 lines of shell around
that. iOS is the same shape again: a `WKWebView` pointed at `snapir::serve()`
running on a thread in the same process.

```
                  ┌─────────────────────────┐
                  │  snapir-core  (C++)     │
                  │  parse · topology ·     │
                  │  planes · solids · STEP │
                  └───────────┬─────────────┘
                              │  one service, three shells
         ┌────────────────────┼────────────────────┐
         │                    │                    │
   Electron + React    Android + WebView     iOS + WKWebView
    (sidecar proc)      (thread, JNI)       (thread, Obj-C++)
```

Nothing under `native/`, `app/` or `snapir/` changes. That constraint is the
design, not a consequence of it: the moment iOS needs its own parser or its own
I/O layer, the reason the C++ core was worth writing is gone.

## What is actually different about iOS

Three things, in descending order of how much they cost.

### 1. It cannot be built on this machine

Not difficult — impossible. `xcodebuild`, `actool`, `codesign` and the iOS SDK
are macOS-only and licensed to Apple hardware. Every line here is authored on
Windows and built on a GitHub Actions `macos-14` runner. There is no local build
step and there will not be one.

The consequence that matters: **the developer cannot open Xcode.** So there is
no `.xcodeproj` in this repo. The project is generated by CMake (`-G Xcode`),
which is a text file that can be written blind and reviewed in a diff.

### 2. The file model does not transfer

The Android app works because `MANAGE_EXTERNAL_STORAGE` plus
`StoragePaths.toFilePath()` turns a `content://` tree back into a real absolute
path, so the unchanged parser can walk a survey folder with `std::filesystem`.

iOS has no equivalent. No all-files access, no real paths outside the sandbox,
and the App Store rejects the shape outright.

Three ways out were considered:

| | Approach | Verdict |
|---|---|---|
| A | Pick a folder, copy it into the sandbox, hand the core a real path | **chosen** |
| B | Read in place behind `startAccessingSecurityScopedResource()` | forces an I/O abstraction into the C++ core |
| C | No picker; operator drags folders into Files.app | least code, worst ergonomics |

**A** is the only one that changes zero lines under `native/`. B would put a
platform seam through the middle of the parser — exactly the property that kept
the Android shell to 692 lines. C is a poor fit for someone walking off an
instrument with a card full of exports.

The copy is cheap: the 28-room reference job is about 4 MB.

### 3. There is no signing and no device

No Apple Developer Program membership, so CI produces an unsigned device build
as a compile check and a **simulator build as the only artifact that runs.**
Signing is added to the same workflow later, when there is an account, without
restructuring anything.

This inverts the build order relative to Android: `arm64-iphonesimulator`
is the primary target, `arm64-iphoneos` is the secondary.

## What gets written

```
ios/
  CMakeLists.txt            app target, bundle, plist, OCCT link
  Info.plist.in
  Sources/
    main.mm                 UIApplicationMain
    AppDelegate.h/.mm       window, root controller
    SnapirViewController.mm WKWebView + status label; the Android MainActivity
    NativeService.h/.mm     snapir::serve() on a thread; HOME; readiness poll
    FolderImport.mm         document picker, scoped bookmark, recursive copy
    WebBridge.mm            WKScriptMessageHandler: pickFolder/reveal/setTheme
  Assets.xcassets/          icon, generated from assets/snapir-mark.svg
native/
  build-occt-ios.sh         the two OCCT cross-compiles
tools/
  build_ios.py              mirrors build_android.py
.github/workflows/
  ios.yml
docs/
  IOS.md
```

Objective-C++ throughout, not Swift. `.mm` calls `snapir::serve()` directly with
no bridging header and no C shim, and one language across the shell means fewer
moving parts in a codebase whose author cannot step through it in a debugger.
The Android shell has no dependencies; this one has none either.

### Mapping, file by file

| Android | iOS | Note |
|---|---|---|
| `MainActivity` | `SnapirViewController` | same three jobs: start service, wait, show web view |
| `NativeService.java` + `jni_bridge.cpp` | `NativeService.mm` | JNI layer disappears; direct call |
| `WebAssets.java` (152 lines) | — | bundle resources are already a real readable path; step deleted |
| `WebBridge.java` | `WebBridge.mm` | `@JavascriptInterface` → `WKScriptMessageHandler` |
| `FolderPicker` + `StoragePaths` (146 lines) | `FolderImport.mm` | system picker + copy; no path reconstruction |
| `network_security_config.xml` | — | ATS does not apply to loopback |

`WebAssets` and `StoragePaths` both exist to fight Android. Neither has an iOS
counterpart, which is most of why this shell should come out smaller than 692
lines.

## How the service starts

The same sequence as Android, with three iOS-specific details.

1. **`web_root` is `[[NSBundle mainBundle] resourcePath]`.** Read-only and
   already unpacked. No install step, no version check, no cache directory.

2. **`HOME` is set explicitly** to `<container>/Library/Application Support`
   before `serve()`. `native/src/store.cpp:61` reads `APPDATA`, then falls back
   to `HOME + "/.config"`. iOS does set `HOME`, to the container root, so
   without this settings land in a hidden directory at the top of the container.
   Same `setenv` trick as `jni_bridge.cpp:52`, different reason.

3. **Port 8765, not negotiable.** The built page pins it in its CSP. Bind
   `127.0.0.1:8765` and poll it exactly as `NativeService.waitUntilReady` does.

No entitlement is needed. `NSLocalNetworkUsageDescription` and the local network
prompt cover LAN discovery and mDNS; loopback is exempt. So is ATS.

**The app is foreground-only.** iOS suspends a backgrounded process and the
listening socket goes with it. For a tool that is used while standing in a room
this is acceptable; the view controller re-checks readiness on
`applicationWillEnterForeground:` and restarts the thread if the socket is gone.

## Importing a survey

```
UIDocumentPickerViewController(forOpeningContentTypes: [UTTypeFolder])
        │
        ├── startAccessingSecurityScopedResource
        ├── recursive copy → Documents/surveys/<name>/
        └── stopAccessing
        │
        └── window.__snapirFolderChosen("<absolute sandbox path>")
```

The page already waits on `window.__snapirFolderChosen`; that contract is
unchanged from `MainActivity.deliverFolder`. What the page receives is a real
absolute path, same as on Android and the desktop.

Exports land beside the input, under `Documents/`. `UIFileSharingEnabled` and
`LSSupportsOpeningDocumentsInPlace` in the plist make the whole tree visible in
Files.app, and `reveal` opens a share sheet on the written STEP rather than the
Android toast.

Re-importing a folder that already exists replaces it, and says so.

## Building Open CASCADE

The existing Android config carries over almost unchanged, which is the payoff
of having every `USE_*` off: no third-party dependency has to be cross-compiled
first, so each SDK is one CMake run.

```sh
cmake -S .deps/occt-src -B .deps/occt-ios-build -G Ninja \
  -DCMAKE_SYSTEM_NAME=iOS \
  -DCMAKE_OSX_SYSROOT=iphoneos \
  -DCMAKE_OSX_ARCHITECTURES=arm64 \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=15.0 \
  -DBUILD_LIBRARY_TYPE=Static -DINSTALL_DIR_LAYOUT=Unix \
  # ...the same BUILD_MODULE_* and USE_* flags as build-occt-android.bat
```

and again with `-DCMAKE_OSX_SYSROOT=iphonesimulator` into `.deps/occt-iossim`.
Both are arm64: the `macos-14` runners are Apple Silicon, so the simulator slice
is `arm64-iphonesimulator`, not x86_64.

**`-Wl,--start-group` must not be carried over.** Apple's `ld64` does not
support the GNU group flags at all;
`android/app/src/main/cpp/CMakeLists.txt:66` fails to link verbatim. It is also
unnecessary — `ld64` resolves circular dependencies between static archives on
its own. The 22 toolkits are listed plainly, in the same order.
`find_library(log-lib log)` is dropped.

## CI

One workflow, `ios.yml`, on `macos-14`.

| Job | Does | Cached on |
|---|---|---|
| `occt` | builds both OCCT SDK slices | OCCT version + a hash of the flag list |
| `app` | web bundle, CMake `-G Xcode`, `xcodebuild` for both SDKs | — |
| `verify` | boots a simulator, installs, runs the reference survey | — |

**Verification is real, not a smoke test.** An iOS Simulator app shares the
host's network stack, so a server bound to `127.0.0.1:8765` inside the simulator
is reachable from the runner at `127.0.0.1:8765`. The job pushes a handful of
reference rooms into the app container (`xcrun simctl get_app_container <udid>
<bundle-id> data`), launches the app, and drives the same HTTP API that
`tools/compare_servers.py` drives. `Daire 53 - Salon` must come back **1 solid,
123 faces, 20.922131 m³** or the job fails.

Simulator matrix: iPad Pro 13-inch first, iPhone 15 second. `xcrun simctl io
screenshot` on both, uploaded as artifacts — the only way to see the app from
Windows, and the same role `tools/shoot_layouts.js` plays for the interface.

**Risk: the OCCT cache.** Two static installs against a 10 GB per-repo cache
limit with LRU eviction. If they do not fit compressed, the fallback is to
publish each install as a versioned release asset and have the workflow download
it — slower to refresh, but not subject to eviction, and the flags change about
once a year.

**Open question — repository visibility.** Public means macOS runners are free.
Private bills macOS minutes at a **10× multiplier**, which makes the OCCT cache
load-bearing rather than merely nice: a cache miss on every push would be an
hour of billed macOS time each time.

## Layout

Universal, iPad-primary. All four orientations rather than the phone's portrait
lock. `tools/shoot_layouts.js` already exercises 800×1180 and 1440×900, so the
React side has tablet layouts under test; this is a target and orientation
change in the plist, not interface work. Deployment target iOS 15.

## What this does not do

- No signing, no `.ipa`, no TestFlight, no App Store submission.
- No hardware verification. Same standing as the APK: built, exercised in a
  simulator, never run on a real device.
- No iCloud, no document browser integration beyond Files.app visibility.
- No background execution.
- No change to `native/`, `app/`, or `snapir/`. If a change there turns out to
  be unavoidable, that is a signal to stop and re-open this design.

## Definition of done

1. `ios.yml` green on a push, from a cold cache.
2. Screenshot artifacts for iPad Pro 13" and iPhone 15 showing the loaded
   interface, not the status label.
3. The reference-survey assertion passing inside the simulator.
4. `docs/IOS.md` written the way `docs/ANDROID.md` is: the plan, then what
   actually happened.
